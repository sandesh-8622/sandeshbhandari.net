## what an operating system actually is

An operating system is the layer of software that sits between the hardware and the applications we use. It manages the processor, allocates memory, handles input and output, talks to storage devices, runs the network stack, enforces security policies, and presents an interface that lets programs and users interact with the machine without having to understand the underlying electronics. Windows, Linux, macOS, Android, and iOS are all examples. So are the smaller specialized operating systems that run inside cars, routers, smart appliances, and the servers that make up the cloud.

The operating system is the most consequential piece of software on any computer, because every other program depends on it. If the operating system makes a slow decision about which task to run next, every application slows down. If it manages memory poorly, applications crash. If it schedules input and output requests badly, storage and network performance collapse. The quality of the operating system determines the practical limit of what the hardware can do, and decades of careful engineering have gone into making these decisions as efficient as possible.

For most of the history of computing, operating systems made these decisions using hand-written rules and heuristics. A scheduler might use a fixed formula to decide which process gets the next slice of CPU time. A memory manager might use a fixed algorithm to decide which page of memory to evict when the system runs out of space. A storage system might use a fixed policy to decide how to organize files on disk. These rules were the product of careful study, and they worked well enough for the workloads of the era in which they were designed. The problem is that the workloads have changed faster than the rules.

## why traditional rule-based design hit a wall

The hardware that operating systems have to manage is no longer homogeneous. A modern server might combine CPUs from one vendor, GPUs from another, specialized accelerators for machine learning, custom networking chips, and various tiers of storage that range from ultra-fast non-volatile memory to slow archival disks. Each of these components has its own performance characteristics, its own optimal use cases, and its own quirks, and a static rule designed for one configuration tends to perform poorly on another. The rules cannot anticipate every combination of hardware that will exist next year, let alone next decade.

The workloads have also become unpredictable. A traditional server might have run a small set of well-understood programs with predictable resource needs, but a modern system might be running hundreds of containerized services, each with different memory and CPU demands, each scaling up and down in response to traffic, each interacting with the others in ways that are difficult to predict in advance. Heuristic-based policies that work well on average tend to fail at the edges, where the unusual workloads live, and the unusual workloads are increasingly common.

The number of competing objectives has multiplied as well. An operating system today is expected to optimize for latency, throughput, energy efficiency, fairness across users, isolation between workloads, and security, all at the same time, and these goals often conflict. Maximizing throughput might hurt latency for individual requests. Maximizing fairness might reduce overall efficiency. Maximizing energy efficiency might slow everything down. Hand-tuned heuristics cannot balance this many competing objectives across the full range of situations the system will encounter, because the optimal trade-off changes constantly depending on what is actually happening on the machine.

Traditional operating systems are reaching their limits as a result. The rules are getting more complex, the configurations are getting more brittle, and the gap between what the hardware could theoretically deliver and what the operating system actually achieves is widening. This is the structural problem that AI in systems work is trying to address.

## the two-way relationship: ai for os, and os for ai

The current research in this area divides into two complementary directions.

The first is called AI for OS, and it refers to using artificial intelligence techniques to make the operating system itself smarter. The idea is to replace static heuristics with models that learn from the actual workload, adapt as conditions change, and make better decisions than a hand-tuned rule could. An AI-driven scheduler might learn the patterns of a particular system and allocate CPU time more efficiently than a fixed algorithm. An AI-driven memory manager might predict which pages will be needed soon and pre-fetch them before they are requested. An AI-driven storage system might learn the access patterns of the applications running on it and reorganize data to minimize latency.

The second is called OS for AI, and it refers to redesigning the operating system itself to better support AI workloads. AI training and inference put unusual demands on a system. They require high throughput between memory and accelerators, low latency for inference requests, efficient coordination across many GPUs, and specialized handling of the large model files that need to be loaded and managed. Traditional operating systems were designed for general-purpose computing, and many of their assumptions break down under these workloads. OS for AI involves rethinking these assumptions and building new abstractions that match what AI systems actually need.

The two directions reinforce each other. As AI becomes more important in the operating system, the operating system needs to support AI workloads more efficiently. As the operating system gets better at supporting AI workloads, more sophisticated AI techniques become feasible within the kernel itself. A feedback loop is accelerating the transformation of both areas.

## ai for os: where ai is being used inside operating systems

The most active area of research is in process scheduling, which is the part of the operating system that decides which task gets to run on which CPU core at any given moment. Traditional schedulers like the Linux Completely Fair Scheduler use static heuristics that work well on average but struggle in heterogeneous environments where some cores are faster than others, some tasks have stricter latency requirements than others, and the right decision depends on the broader state of the system. Small neural networks embedded directly in the kernel can imitate these scheduling decisions with very low inference overhead while delivering significant improvements in resource utilization and task completion times.

The input and output layer is another area where AI is making a difference. Storage devices like solid-state drives have complex internal behaviors that traditional schedulers cannot model accurately, producing high tail latency: most requests are fast, but the slow ones are unpredictably slow. Lightweight neural networks embedded in the I/O path can predict which requests will be slow before they are issued, allowing the system to route or schedule them differently and significantly reducing worst-case latency. Some implementations have shown latency reductions of up to forty percent on real workloads.

Memory management is a third area where the limits of traditional heuristics are obvious. Modern memory hierarchies include multiple tiers, from fast caches to main memory to non-volatile storage, and the optimal placement of data across these tiers depends on access patterns that are difficult to predict in advance. Reinforcement learning approaches have been used to train memory managers that learn the access patterns of specific workloads and place data accordingly, achieving substantial improvements in both performance and energy efficiency. Some of these approaches focus on virtual memory address mapping, where the goal is to make better use of advanced hardware features like 3D-stacked memory that traditional algorithms underutilize.

Storage management benefits from AI in a similar way. Decisions about which data to compress, which to cache, which to migrate between storage tiers, and how to lay out files for fast access can all be informed by machine learning models trained on the actual usage patterns of a system. The improvements are particularly significant in environments with mixed workloads, where the optimal storage policy for one application conflicts with the optimal policy for another.

The network stack is another rich area. Network performance depends on hundreds of variables, including link quality, congestion, packet loss, and the behavior of remote endpoints, and traditional rate-adaptation algorithms make conservative choices that leave performance on the table. Machine learning approaches to rate adaptation have shown improvements of several hundred percent over heuristic methods in some wireless environments, by learning the patterns of specific networks and adjusting transmission strategies accordingly.

Security is being transformed by AI as well, though the transformation is more cautious because the stakes are higher. Intrusion detection systems use machine learning to identify anomalous behavior that hand-written rules would miss, malware classifiers use deep learning to recognize new variants of known threats, and behavior-based authentication systems use AI to spot suspicious patterns in user activity. The same techniques can be used by attackers, so the security arms race in operating systems is increasingly a competition between AI systems on both sides. Adversarial machine learning, where attackers deliberately craft inputs that fool detection models, is a serious concern, and security-focused AI in operating systems has to be designed with the assumption that someone will try to subvert it. The defenses are evolving, including techniques like adversarial training, model ensembles, and hybrid approaches that combine learned models with hand-written rules for the cases where the consequences of being wrong are highest.

The graphical and command-line interfaces are also changing. Large language models are being integrated into shells and terminals to translate natural-language requests into precise commands, into installers to guide users through complex setup processes, and into help systems to provide context-aware assistance. The interface layer is where most users actually experience the operating system, and making it more intelligent has a disproportionate effect on perceived quality.

Beyond the core kernel, the broader ecosystem is also being reshaped by AI. Writing kernel code is being supported by AI assistants that can generate, review, and debug low-level code, which has historically been one of the most difficult and error-prone areas of software engineering. Kernel code has to be efficient, has to handle concurrency correctly, has to deal with hardware quirks, and has to be secure against attacks, and getting all of this right requires years of specialized experience. AI coding assistants trained on kernel code are beginning to help with this work, suggesting fixes, identifying potential bugs, and generating boilerplate that would otherwise consume engineering time.

System tuning, which used to require deep expertise and a great deal of trial and error, is being automated by tools that learn the optimal configuration for a particular workload and adjust parameters automatically. A modern operating system has hundreds or thousands of tunable parameters, from cache sizes to scheduler weights to network buffer settings, and the right values depend on the workload, the hardware, and the goals of the deployment. Machine learning approaches to tuning can explore this parameter space efficiently, finding configurations that hand-tuning would miss and adapting them as conditions change, giving systems better performance with less human intervention.

Formal verification, the process of mathematically proving that a piece of code behaves correctly, is being supported by AI tools that can suggest invariants and help structure proofs. Verification has traditionally been one of the most labor-intensive parts of building reliable systems, requiring specialists to write proofs that can take years to complete for a single kernel module. AI assistance is starting to make this work faster and more accessible, which matters because the parts of the operating system most critical to security and reliability are exactly the parts where verification is most valuable.

Even the education of new systems programmers is changing. AI tutors that can walk a learner through specific kernel data structures, explain why a particular function is written the way it is, and answer follow-up questions in real time can compress a learning process that has historically been slow and unforgiving. The barrier to entry for systems work has always been high, and that is starting to shift.

## the three categories of ai tools used in systems work

Not all artificial intelligence is the same, and the choice of which kind of AI to use for a particular systems problem matters enormously. Three main categories are currently in use, each with different strengths, weaknesses, and appropriate applications.

Traditional machine learning is the oldest and most widely used, including techniques like decision trees, support vector machines, random forests, neural networks, and reinforcement learning. These methods typically work with structured data and produce outputs that are fast, predictable, and relatively easy to deploy in a kernel context. A small neural network can make scheduling decisions in microseconds, fast enough to run in the kernel without slowing down the system it is supposed to be optimizing. The downside is that these models are usually narrow. They are trained for specific tasks and tend to perform poorly when the workload changes in ways the training data did not anticipate.

Large language models have become important in systems work over the past few years. LLMs bring capabilities that traditional machine learning cannot match, including the ability to reason about code, understand natural language descriptions of problems, generate explanations of system behavior, and adapt to new situations through prompting rather than retraining. But LLMs are too slow and too expensive to run in performance-critical paths inside the kernel. A scheduling decision that has to happen in a few microseconds cannot wait for an LLM to think about it. LLMs in systems work are typically used at higher levels of abstraction, for tasks like writing configuration files, explaining diagnostic information, or assisting with system administration.

Agent-based intelligence is the third and newest category. It combines LLMs with the ability to perceive the environment, plan sequences of actions, invoke external tools, and coordinate with other agents. An agent in this context is not just a model that produces an output. It is a goal-directed system that can decompose a complex objective into smaller steps, execute those steps using whatever tools are available, and adapt its plan based on the results. Agents are being used for tasks like end-to-end system debugging, automated tuning of complex configurations, and coordinated management of large distributed systems. They are also even slower and more resource-intensive than the LLMs at their core, making them poorly suited for anything that has to happen on a fast timescale.

The progression from traditional ML to LLMs to agents is not a hierarchy of better and worse. It is a set of different trade-offs. Traditional ML is fast and predictable but narrow. LLMs are flexible and capable of reasoning but slow. Agents are autonomous and adaptable but expensive. The right choice depends on where in the system the AI is operating and what kind of decision it is making.

## how to choose between the three categories

Four dimensions shape the choice of AI technique in systems work, and they often pull in different directions.

Efficiency and overhead is the first. Some decisions in an operating system have to happen in microseconds, while others can take seconds or even minutes. A scheduler choosing the next process to run has a microsecond budget. A system configuration tool reorganizing storage tiers has a longer budget. Traditional machine learning is the only option for the fast end of this spectrum. LLMs work for the slow end. Agents are usually only appropriate for tasks that span minutes or longer.

Versatility is the second. A model trained for one specific task cannot easily be applied to another. Traditional machine learning models tend to be narrow specialists, while LLMs and agents can handle a wider range of tasks because they can reason about new situations rather than just pattern-matching against trained examples. In an environment where the workload changes frequently or the requirements evolve over time, the broader capabilities of LLMs and agents become more valuable, even at the cost of higher overhead.

Interpretability is the third. When something goes wrong in an operating system, engineers need to understand why the system made the decision it did. Traditional machine learning models are often opaque, producing outputs without clear explanations. LLMs can generate human-readable explanations and rationales, which makes them easier to debug and audit. Agents go further, producing explicit reasoning traces and tool-call histories that show exactly what they did and why. As operating systems become more autonomous, this kind of auditability becomes more important, both for engineering reasons and for trust.

Numerical capability is the fourth. Many decisions in an operating system involve precise quantitative reasoning, like calculating the optimal allocation of a fixed resource across competing demands. Traditional machine learning, particularly when trained with the right loss functions, tends to be more accurate at this kind of numerical work than LLMs or agents, which can produce confident-sounding answers that are quantitatively wrong. For decisions that depend on getting numbers right, traditional ML usually remains the better choice.

Real systems are likely to use combinations of all three, with each one applied where it makes sense: traditional ML in the performance-critical kernel paths, LLMs in the higher-level decision-making layers, and agents for long-running orchestration and administration tasks. Integrating these different kinds of intelligence into a coherent whole is one of the central open problems in the field.

## os for ai: how operating systems are being redesigned for ai workloads

The other direction of the relationship is about redesigning the operating system itself to handle AI workloads better, and it is moving fast because the workloads have outgrown the traditional abstractions.

At the component level, several specific subsystems are being adapted. The scheduler is being rebuilt to handle the unusual patterns of AI workloads, where short-context inference requests need micro-scale dispatch latency, distributed training jobs need macro-scale synchronization across many nodes, and these conflicting requirements have to coexist on the same machine. Traditional batch-oriented schedulers that optimize average throughput tend to ignore tail latency and cross-device balance, both of which matter enormously for AI work. New schedulers are being designed to be aware of the semantic structure of AI workloads and the hardware they are running on, allowing them to make decisions that traditional schedulers cannot.

Memory management is being adapted for the unusual memory patterns of large models, which can be hundreds of gigabytes in size and need to be moved efficiently between system memory, accelerator memory, and storage. Specialized memory allocators, paging strategies, and prefetching policies are being developed to handle these workloads, often by abandoning the assumption of uniform memory access that traditional operating systems were built around. Faster model loading, more efficient use of expensive accelerator memory, and lower overhead for memory-intensive operations follow from this work.

Networking is being rebuilt around the demands of distributed training, where the time spent moving gradients between machines can dominate the time spent doing useful computation. Kernel-bypass networking allows applications to send and receive data without going through the kernel at all, which eliminates the overhead of system calls and context switches and dramatically improves throughput. Specialized network protocols designed for AI workloads are starting to replace general-purpose protocols in environments where the gain in performance justifies the loss in generality.

Storage systems are being redesigned to handle the access patterns of AI workloads, where huge datasets need to be streamed efficiently into training jobs and where model checkpoints need to be saved and loaded quickly. The traditional file system abstraction, with its emphasis on POSIX semantics and small-file operations, is poorly matched to these requirements. New storage systems built for AI emphasize bulk throughput, parallel access, and specialized formats that match the needs of training frameworks.

At the architecture level, the changes are even more significant. Library operating systems, which package an entire OS into a single application as a set of library calls, eliminate much of the overhead of traditional operating systems and allow applications to be tuned for their specific workloads. Unikernels, which compile a single application together with the minimum operating system functionality it needs into a single bootable image, take this approach even further. These designs sacrifice generality for performance, and they make sense in environments where a specific AI workload is going to be running on dedicated hardware.

Accelerator-aware scheduling and resource management is becoming central to OS for AI work. Modern AI workloads depend heavily on GPUs and specialized accelerators, and the traditional operating system abstractions for managing these devices were retrofitted onto designs that originally assumed everything ran on the CPU. New architectures are being built that treat accelerators as first-class resources, with kernel mechanisms designed specifically to coordinate their use, manage their memory, and allocate their compute capacity across competing workloads.

Edge inference is a particularly interesting subcategory, because the constraints are completely different from those of cloud deployment. An AI model running on a phone or a smart appliance has to work within tight memory and energy budgets, often without network connectivity, and the operating system has to balance the demands of the model against everything else the device is doing. Specialized operating systems for edge AI are being developed that include model compression, quantized inference, and adaptive resource management as core capabilities rather than as add-ons. Some of these systems share the same model across multiple applications, paging different parts of it in and out of memory based on what is needed at any given moment, which can dramatically reduce the resource cost of running AI on constrained devices.

Long-context inference is another area where the operating system has to adapt to unusual workload characteristics. Modern language models can handle context windows of hundreds of thousands of tokens, and the memory required to hold this context grows rapidly with its size. Operating system support for efficient KV cache management, where the intermediate representations of long contexts are stored and updated, has become a significant area of work. Approaches include hierarchical caching strategies, where frequently accessed parts of the context stay in fast memory while less frequently used parts move to slower tiers, and selective offloading techniques that move parts of the cache to disk or to other devices when memory pressure rises.

Distributed training is the workload that has driven the largest architectural rethinking. Training a large language model can require thousands of GPUs working in coordination for weeks or months, and the synchronization overhead between these devices can become the dominant cost if the operating system does not handle it efficiently. New scheduling approaches, communication libraries, and resource managers are being developed specifically for this kind of work, often making trade-offs that would be unacceptable in general-purpose computing but that are appropriate when the workload is well-defined and the goal is to maximize throughput on a single dominant task.

## the three-stage roadmap

The research community has converged on a rough roadmap for how the integration of AI and operating systems will progress over the next decade or two. The roadmap has three stages, each representing a deeper level of integration than the last.

The first stage is the AI-Powered OS, which is essentially what we have now. AI is added to an otherwise traditional operating system as a set of intelligent modules that enhance specific functions without changing the underlying architecture. The scheduler might have an ML model attached to it, the I/O layer might use a neural network for admission control, and the user interface might be supplemented with a large language model for natural-language queries, but the operating system itself is still built around traditional abstractions and traditional mechanisms. The AI is a layer of intelligence on top of a fundamentally pre-AI design.

The AI-Powered OS is the easiest stage to reach because it does not require rebuilding any of the existing infrastructure. It also cannot do as much as it could, because the system it is enhancing was not designed to take advantage of intelligent decision-making. The improvements tend to be incremental, focused on specific subsystems, and limited by the constraints of the underlying architecture. Most current work falls into this stage.

The second stage is the AI-Refactored OS, which involves a deeper architectural transformation. Intelligent mechanisms are integrated into the structure of the operating system itself, not just bolted on top of it. The kernel interfaces are designed to be AI-friendly from the ground up, the scheduling and memory management subsystems are built around the assumption that they will be controlled by models rather than by static rules, and the boundaries between components are redrawn to make it easier for AI to coordinate decisions across them. This stage requires significant investment because much of the existing infrastructure has to be rebuilt, but the payoff is an operating system that can take much fuller advantage of AI techniques than the AI-Powered design can.

The AI-Refactored OS is the stage that most of the ambitious current research is trying to reach. Projects in this space include modular kernel architectures designed for AI integration, unified toolchains that span the boundary between AI development and systems development, and hybrid decision frameworks that combine static rules with learned models in a coordinated way. The technical challenges are substantial, but the direction of travel is clear.

The third stage is the AI-Driven OS, which represents the full transformation. At this stage, the operating system is not just enhanced or refactored to support AI. The operating system itself is driven by AI at every level, with embedded models making most of the decisions and human-written rules playing a secondary role as guardrails. The kernel is something closer to a learned system than to a programmed one, capable of adapting its behavior to new workloads, new hardware, and new requirements without explicit reprogramming.

The AI-Driven OS is mostly speculative at this point. A few experimental systems exist that point in this direction, but the technical challenges of making such a system reliable, predictable, and secure are substantial. The reason this stage matters is that it represents the eventual destination of the current trajectory, and thinking about what such a system would require helps clarify what needs to be solved between now and then.

The progression from AI-Powered to AI-Refactored to AI-Driven is not a hard sequence that every system has to follow. Different parts of the operating system may move at different speeds, and some systems may skip stages entirely depending on their requirements. The roadmap is a framework for thinking about the trajectory, not a strict timeline.

## the problems that have not been solved

The integration of AI into operating systems faces several serious problems, and being honest about them matters because they shape what is actually possible in the near term.

Complexity is the most immediate. An operating system that combines static rules, machine learning models, large language models, and agent-based intelligence is significantly more complex than one that relies on rules alone. Debugging such a system is harder, understanding its behavior is harder, and maintaining it over years of evolution is harder. The complexity is not just additive, either. The interactions between different intelligent components can produce emergent behaviors that none of the components would produce on their own, and predicting these interactions is one of the open problems in the field.

Performance overhead is a closely related constraint. AI techniques add computational cost, and that cost has to be paid every time the AI makes a decision. A neural network that adds two microseconds to every scheduling decision might be worthwhile if it improves overall efficiency by ten percent, but if the system makes a million scheduling decisions per second, the total cost adds up fast. Managing this overhead is an active area of research and a significant limit on how much AI can actually be deployed in performance-critical kernel paths.

Then there is model drift. A machine learning model trained on the workload of a system at one point in time will start to perform worse as the workload changes, because the patterns it learned no longer match the patterns it is seeing. Operating systems run for years, and their workloads evolve continuously, so any AI integrated into them has to be retrained or updated regularly to remain effective. The infrastructure for monitoring drift, deciding when to retrain, and deploying updated models without disrupting the running system is still being developed.

Interpretability is a harder problem than it might look. When a static rule makes a bad decision, an engineer can read the rule, understand why it produced the wrong output, and fix it. When a learned model makes a bad decision, the path to understanding why is often much harder. The model might be a black box whose internal representations do not correspond to anything human-readable. Without some way to explain the decisions that an AI-driven operating system is making, debugging becomes difficult and trust becomes harder to establish, and the willingness of engineers to deploy such systems in critical environments will remain limited.

Privacy and safety are a fifth problem, and one that tends to be underestimated. An operating system has access to enormous amounts of sensitive data, from the contents of files to the patterns of user behavior. AI models trained on this data raise privacy concerns that traditional operating systems did not have. Models can leak information about their training data, can be attacked by adversaries who manipulate their inputs to produce harmful outputs, and can be subverted in ways that traditional rule-based code cannot. The security and privacy implications of AI in operating systems are still being mapped out, and the regulatory environment around this is likely to become much more demanding over the next several years.

There is also a more strategic tension that gets less attention: the conflict between hardware specialization and software portability. AI workloads benefit enormously from specialized hardware, but operating systems that are tightly coupled to specific accelerators tend to lock applications into specific platforms. The history of computing has repeatedly shown that excessive specialization creates fragility, while excessive generality leaves performance on the table. Finding the right balance for AI-aware operating systems is an open design question, and the answer will probably differ across deployment contexts. A research lab running a few well-defined training workloads can accept tight hardware coupling. A cloud provider supporting thousands of different applications cannot.

None of these problems is fatal, but all of them are imp, and progress on integrating AI into operating systems will be paced by progress on these problems as much as by progress on the AI techniques themselves. The current excitement about AI in systems work sometimes obscures the fact that the field is still early, and many of the most important questions about how to do this well have not been answered yet.
